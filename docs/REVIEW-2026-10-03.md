# PC TeleRC full code review — 2026-10-03

Scope: all Python runtime modules, tests, dependency pins, PyInstaller/Inno Setup configuration, CI workflow, operator documentation, and the sensitivity slider change. Review base: f71a2c863c1844a7bf9be204bc3c1f75df049226. No Android or ESP32 source was modified.

## Findings and corrections

| Severity | Verified finding | Correction |
| --- | --- | --- |
| High | An in-flight control tick could send a drive override after Disable's release sequence. | Serialize the full tick and control/configuration transitions with the same reentrant send lock. |
| High | Standard pymavlink UDP writes swallow socket errors; RC success could be reported despite a local send failure. | Dedicated single-socket transport propagates errors to the existing control failsafe. |
| High | Dynamic UDP writes broadcast to all learned clients; its last-address check also prevented GCS heartbeats on the normal UDP server path. | Unicast to the accepted vehicle peer; fixed-IP receive filtering and source endpoint pinning; explicit destination availability. |
| High | Pending network restart could survive Apply Settings while ARM/control became available; Apply Settings could also prematurely change the live destination. | Keep pending network settings inactive and block ARM/control until explicit reconnect. |
| High | Settings changes could retain a frame computed with the previous mapping; fast controller detach/reconnect could escape a GUI poll. | Invalidate frames on configure/selection and track controller connection generations. |
| High | NaN input can turn clamping into full-scale values; overlapping axes can couple steering and pedals. | Reject nonfinite/out-of-range readings, malformed settings, future/invalid frames, and overlapping controller axes. |
| High | A delayed worker could resume from newly fresh input after a scheduling stall/suspend. | Control tick deadline misses latch control OFF. |
| Medium | No Disconnect button; stopped transport retained a connected snapshot; target changes could keep the old vehicle identity. | Explicit Disconnect, closed socket and reset identity/heartbeat, fresh session on reconnect. |
| Medium | Monitor-only disconnect sent neutral/release and could interrupt another controller. | Only send RC shutdown sequence when PC control owns the override. |
| Medium | DISARM left PC override transmission active; commands did not surface ACK rejection or a confirmation timeout. | Disable/release first; report rejected ACK, heartbeat confirmation, and a 5-second confirmation timeout. |
| Medium | Calibration could accept samples on one side of neutral or unsupported pedal ranges, and reuse stale snapshots. | Validate finite samples, neutral bracketing, supported normalized ranges, fresh distinct samples, and controller continuity. |
| Medium | Settings save errors escaped UI handlers; diagnostics had an unowned timer callback touching a deleted widget. | Recoverable save failure with pending state retained; parent-owned single-shot timer. |
| Medium | UDP SO_REUSEADDR allowed shared listener ownership. | Exclusive Windows bind and no socket reuse; disable Windows UDP connection-reset notifications. |
| Low | README executable path and live-target/reconnect behavior no longer matched code. | Update packaging and connection documentation. |

## Operator workflow

1. Join the ESP32 rover Wi-Fi network and start PC TeleRC. The listener starts automatically; control remains OFF.
2. Select and calibrate the PXN wheel; apply settings. Only one identical-GUID wheel may be connected because SDL GUIDs identify device models rather than uniquely identifying each physical unit.
3. If network fields were edited, click Apply & Connect/Reconnect. Wait for a fresh ArduRover autopilot heartbeat and fresh neutral pedal input.
4. ARM explicitly if required. Observe vehicle confirmation or rejection; sending a request is not arming confirmation.
5. Enable PC Control manually. CH1 steering and CH2 drive overrides run at 20 Hz. Steering sensitivity changes gain after deadzone/expo; throttle limit stays independent.
6. Disable PC Control for transmitter handover: send neutral then release the two mapped channels. Telemetry remains connected. Release packets use 0 for the mapped channels and 65535 for untouched channels.
7. Disconnect: release if owned, stop GCS heartbeats, close UDP. This does not disarm; the configured flight-controller GCS failsafe may activate when GCS heartbeats stop.
8. Reconnect: open a new session; wait for new heartbeat/input; manually enable control again. No automatic arming or resume occurs.

## Validation

- 80 tests passed locally; syntax compilation and pip dependency integrity check passed.
- Real loopback UDP: rover acquisition, exact MAVLink 1 system 255/component 190 CH1/CH2 drive commands, untouched CH3, neutral/release order, actual socket closure/port reuse, and reconnect without control resume.
- Deterministic concurrent tick/disable test: Disable cannot finish while an earlier drive send is blocked, and no drive packet follows the final release.
- Fault injection: stale/lost/invalid controller frames, scheduling stall, local UDP send failure, mapping changes, pending network settings, settings-save failure, and ARM/DISARM feedback.
- Multi-peer UDP tests: no command broadcast, no foreign-peer heartbeat admission after peer lock, original sender preserved across multi-message datagrams, and exclusive listener bind.
- Headless Qt layout inspected with the application stylesheet.

Local execution is Linux with Python 3.12 and the pinned runtime dependencies. Windows CI must validate the Windows-specific socket options, wheel driver integration, PyInstaller executable, and installer. No physical PXN/ESP32/SpeedyBee/motor-driver test was available here.

## Remaining limits

- MAVLink 1 commands have no signing/authentication or encryption. IP/port pinning reduces accidental cross-talk but cannot defeat IP spoofing or an attacker already on the rover network. Dynamic mode trusts the first valid ArduRover heartbeat; prefer a fixed ESP32 address. MAVLink signing requires a coordinated MAVLink 2 bridge change.
- Successful UDP send confirms local transmission only. RC overrides have no delivery ACK. True Wi-Fi-loss protection and transmitter handover still depend on the bridge watchdog and ArduRover's RC override/GCS failsafe configuration.
- A bridge reboot that changes its UDP source port requires manual reconnect. The app deliberately does not silently select a new peer.
- The existing bridge protocol provides no ownership negotiation between Android and PC controllers. Use one active control application at a time.
- Calibration selects normalized axes and inversion; it does not implement arbitrary offset/range remapping for unusual PXN driver modes. Unsupported ranges are rejected rather than accepted with misleading output.
- Dependency integrity and a source credential/execution-path scan passed; this is not a third-party dependency vulnerability audit or a penetration test. The Windows installer remains unsigned.
- Bench validation still required: CH1/CH2 direction and magnitude, actual RC transmitter takeover, measured controller-unplug and Wi-Fi-loss stop times, cold start/repeated reconnect, and Windows sleep/resume.
