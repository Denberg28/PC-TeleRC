# PC TeleRC v0.1.0a9 — MAVLink Bridge-Control Compatibility

This maintenance prerelease fixes the control-path mismatch discovered during bench testing with the ESP32-S3 TeleRC bridge.

## Root cause
ArduRover emits MAVLink 2 telemetry. pymavlink auto-detects that stream and can switch the connection's transmitter to MAVLink 2. The TeleRC ESP32 command filter intentionally accepts the established Android control envelope: MAVLink 1 from system 255 / component 190.

Result before this release:
- heartbeat/telemetry worked,
- PC TeleRC showed Connected / ARMED / PC CONTROL ACTIVE,
- TX increased,
- but RC_CHANNELS_OVERRIDE could be rejected by the bridge because the outgoing packet had switched to MAVLink 2.

## Fix
- Receive path remains MAVLink 1/2 auto-detect.
- All bridge-facing control traffic is explicitly encoded as MAVLink 1:
  - GCS heartbeat
  - ARM / DISARM
  - RC_CHANNELS_OVERRIDE
  - neutral packets
  - release packets
- Source identity remains sysid 255 / compid 190.
- Sparse override semantics remain intact: commanded channels carry PWM values while unused CH1-CH4 fields use 65535.
- Added wire-format regression tests that assert:
  - MAVLink 1 magic byte 0xFE,
  - message ID 70 for RC_CHANNELS_OVERRIDE,
  - sysid 255 / compid 190,
  - correct sparse channel encoding.

## Compatibility
- Android TeleRC app code is unchanged.
- Use the updated ESP32 bridge sketch that accepts sparse CH1-CH4 overrides.
- CH5-CH8 remain protected by the bridge and are not remotely overridden.

## Bench test
With wheels lifted:
1. Flash the latest TeleRCBridge.ino.
2. Install PC TeleRC v0.1.0a9.
3. Connect to TeleRC-Rover.
4. Confirm heartbeat and ARMED state.
5. Enable PC Control.
6. Turn the PXN wheel and verify PC TeleRC CH1 changes.
7. Confirm Mission Planner RC_CHANNELS chan1_raw changes when connected separately over USB/COM.
8. Test throttle only after steering is confirmed.

This is still a prerelease pending full physical fail-safe validation.
