# PC TeleRC v1.2.0rc7 — Stored FC mission inspection

Application-only candidate based on the exact published v1.2.0rc6 source. Install
the Windows update or run the portable PC-TeleRC.exe. Fleet firmware 0.5.0rc1,
PWM converter 1.0.5 and private pairing remain unchanged. rc6 is retained as the
mission-planning baseline and rollback release.

## Load from FC

Connect the selected rover, then choose Load from FC. The application reads its
stored mission and opens a modeless, read-only snapshot with row numbers,
commands, coordinates/parameters and read time. Empty or home-only FC storage
is displayed correctly. Unknown commands remain inspection data; they are never
converted into an executable PC draft.

The PC draft is unchanged. Loading clears previous upload verification and never
authorizes Arm or Start. HOLD remains accessible. A late result from a closed,
reconnected or differently selected rover is ignored. Changing rover,
disconnecting or beginning an accepted replacement upload closes the viewer.

## Transfer behavior

Read requests have bounded retries, additional relay response time, progress,
sequence filtering and a total deadline capped at ten minutes. A final count and,
when supplied by the FC, opaque mission-id check rejects changes during transfer.
No partial snapshot is displayed. The shared BASE still allows only one
foreground mission transaction; other admitted rovers remain monitored.

An incomplete read with fresh real telemetry returns to monitor-only service;
it does not command a running rover to stop. Actual telemetry loss, USB/route
failure and the UI lease still cancel the session under the existing loss policy.
HOLD interrupts the read; inspection never queues or retries START.

## Replacing a mission

Upload & verify requests replacement of the selected FC's stored mission. It
requires disarmed MANUAL/HOLD, a deliberate confirmation, FC acceptance and full
readback comparison. No separate clear/delete command is sent first. The PC
must consider an interrupted upload unknown and require a fresh verified upload;
it must not assume either the old or replacement mission is intact.

There is no automatic rollback, arm, start or resume. A loaded snapshot is a
point-in-time view, not a live mission database or start authorization. Another
GCS can change FC storage; review and upload/verify deliberately before operation.

The request/item/ack flow and retry handling follow the
[MAVLink Mission Protocol](https://mavlink.io/en/services/mission.html). This is
not a claim of certification, RF-range qualification or atomic storage rollback
on the specific FC.

## Verification boundary

The release is gated on current Windows regressions, frozen executable checks,
read-only/drop/duplicate/cancellation and rover-isolation tests, unchanged
firmware hashes, sanitation and downloaded-asset checksums. The Windows runner
uses isolated native test processes, with no skipped failures or automatic
retries. Complete source and evidence are included. Existing eleven board-build
records are reused for unchanged firmware. Physical long-range RF, motor,
stopping and handset-takeover acceptance remain pending.
